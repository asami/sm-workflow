# RepositorySync maintenance continuation

The maintenance candidate starts from the completed deployed Phase 6.10 release.
It retains the existing native Session, continuation identities, immutable issued
inputs, protected history and accepted results. It introduces no new Task,
recovery API, grouping authority or history migration.

Ordinary complete UTF-8 text has no duplicate application byte ceiling in purpose
capture, proposed content, assigned conflict text, repair text, review rationale
or retained validation output. CNCF owns configured acquisition/output budgets.
NUL, invalid UTF-8, binary or unavailable native content, truncated output,
inconsistent byte counts and foreign paths remain refused at their existing
owners. Conflict and repair file inventories have no duplicate application
count ceiling; complete exact path coverage and ordinary-text checks still
apply. Unrelated operation and GoalPhase limits retain their existing meaning. Review
inline preview settings remain presentation settings and grant no acceptance.

New repair-scope correction observations use explicit policy v3 without a
`maximumFiles` field. An unprepared target returns `preparation-required`, no
Human choices and `prepareRepositorySyncRepairScopeCorrection` as its next
operation. Runtime preparation qualifies the supplied complete existing file
inventory against the same failed candidate through typed Git/File operations.
Only that prepared target exposes lifecycle-only adoption; the Human supplies
actual prior-worker-ended and UNKNOWN acceptance evidence with empty answer
paths. File selection requires no Human grant. Adoption reobserves the exact
prepared target and preserves its Session, revisions, claim status, subject and
candidate freshness checks. Separate ordinary Advance captures the fixed
inventory and materializes through the same admission without splitting or
truncating files or reacquiring diagnostic output through SBT.

Historical v1/v2 targets and directions retain their actual `maximumFiles`
integer and original count restrictions. They are not migrated or relaxed.
Canonical v3 excludes the field, old versions require it, and explicit null,
unknown or cross-version fields refuse. Original UNKNOWN effects, check
receipts, history and repair accounting remain unchanged.

Focused source specifications include 33-conflict admission, 251-file repair
admission, 129-file typed File capture/application with expected-text mismatch
refusal, and v1/v2 versus v3 canonical and preparation/adoption boundaries.
These authored scenarios require parent-selected validation; their presence
does not claim execution, installed delivery or live Human acceptance.

The normal packaged Git repository declaration and the maintenance fixture's
selected Git declarations omit `stdinBytes` and `stdoutBytes`. CNCF's process-plan
codec allows omission of `stdinBytes`, `stdoutBytes` and `stderrBytes`; each
omitted stream inherits the configured `cncf.io.default-maximum-bytes`, falling
back to 1 MiB (1,048,576 bytes) when the common setting is absent. An individual
setting takes precedence over the common setting, which takes precedence over
the built-in default. The common setting is a default, not a cap: explicit
smaller or larger finite values remain authoritative. The packaged Git
declaration retains its explicit `stderrBytes`; its actual omissions are stdin
and stdout only. The other eight process limits remain mandatory, and SBT's
explicit output budgets remain unchanged. File read and file write independently
follow the same individual-over-common-over-built-in precedence. The fixture
retains its finite artifact budget.
Resource admission is owned by CNCF, as specified in
`docs/spec/process-execution-runtime.md` in the CNCF repository: each Git step
validates its actual stdin and captures its actual bounded stdout. Expected
worktree content and selected content are distinct values; their sum is neither
stream's byte count. CNCF retains its finite individual worktree-read and actual
aggregate WorkArea guards, along with complete capture/termination checks.

Earlier qualification applies only to its recorded inputs and configuration,
including the fixture's prior stdin increase. A fixture-only stream increase
does not establish removal of the synthetic aggregate comparison. The CNCF
aggregate-admission correction and replacement of the fixture-only stream
workaround with normal host defaults require qualification of the affected
direct and installed paths. The direct
`Equal` case and the explicit installed same-Session purpose-to-conflict case
now use 775,000-byte ordinary UTF-8 purpose text. Each actual content payload is
below 1 MiB while expected-plus-selected content totals 1,550,000 bytes, above
either default stream ceiling. Their new assertions make that distinction
explicit; qualification must exercise those changed cases.

A retained purpose inventory with the exact historical diagnostic
`binary or oversized worktree text remains unexamined` may receive its first
completion when its worktree text is present and ordinary UTF-8 without NUL,
and every present original/indexed text is independently ordinary UTF-8 without
NUL. Admission leaves that diagnostic, input and history unchanged. Missing
worktree text, other diagnostics, binary/unavailable native blobs, malformed
Unicode and NUL do not gain this compatibility exception.

The actual unsuspended `MergeConflicted`, `MergeResolutionAdmitted` and
`ConflictDecisionRequired` frontiers dispatch directly to the existing conflict
continuation before fetch reuse, fallback progression or purpose capture. Without
that port, Advance returns the retained conflict Wait without effects. A completed
purpose is a historical result after integration starts. Only a frontier selected
by the existing Purpose lifecycle may select a current purpose candidate for
review, repair or conflict-path scope.

When integration first observes a conflict after installing a purpose, it returns
the retained conflict Wait. That call's conflict port was configured before
purpose completion and may still name only the purpose's paths. The next public
Advance binds the actual unmerged paths before issuing the conflict WorkOrder.
Routes that did not install a purpose retain their existing immediate dispatch.
Historical native-review/native-triage contexts select merge scope only when
their safely parsed source revision names an actual `MergeValidated` entry in
the same instance history. Past purpose review does not supply merge scope;
historical genuine merge review remains available to the existing repair path.

A later Advance issues the genuine conflict WorkOrder in the same Session.
Repeated Advance before Submit retains that context without another purpose
commit, merge attempt or write-tree on the unmerged index. Genuine Submit uses
the original issued context. Later Advance materializes only that proposal and
uses the existing validation, independent semantic review, native merge commit,
push and final fetch. Repeated collection after Terminal is passive.

Native ordinary-text conflict capture accepts exactly one index row at each of
stages 1/2/3 (modify/modify) or 2/3 (add/add), with the same regular-file mode
100644 or 100755 on every row. An add/add conflict has no base: its optional
`base` is absent rather than an invented empty blob or object identity. A real
stage-1 blob whose text is empty remains a present base with its actual identity.
Deletion, missing or duplicate required stages, mismatched or symlink modes,
binary content and malformed or incomplete text remain refused. Observation
does not resolve files or grant command authority.

The semantic conflict input retains type identity `RepositorySyncConflictRequest`.
Inputs whose conflicts all have bases keep the existing
`sm-workflow.repository-sync-conflict-request.v1` wire shape, including each
base blob object. An input with any absent base uses
`sm-workflow.repository-sync-conflict-request.v2`; its optional base can be JSON
null or omitted on read. Legacy v1 input with a missing or null base is refused.
The nested Human input follows the same rule with
`sm-workflow.repository-human-conflict-input.v1` and `.v2`, retaining type identity
`RepositorySyncHumanConflictRequest`. Unknown versions are refused. Semantic
result and Human answer schemas remain v1. No retained record is rewritten or
migrated. Public conflict output exposes the optional base, and Human evidence
binds the original base identity string when present or JSON null when absent.
Standard public Record transport may omit that optional null field; Human
selection canonicalizes omission or null to JSON null while preserving an
actual base identity string exactly.
Malformed optional values do not supply Human evidence or admission authority.

`RepositorySyncMaintenanceContinuationSpec` exercises direct public Operations
with real local/bare repositories, complete large purpose content, a conflict
outside the last purpose, retained history and native Git observations through
final convergence, including a required independent purpose review before
installation and a separate later merge review. Nearby text-contract specs retain malformed and truncated
capture regressions. `Phase69DirtyPurposeSpec` checks the retained legacy input
compatibility rule. Authored proposal and independent-review responses are
specification fixtures and do not attest live provider or Human acceptance.

The direct `MixedAddAdd` scenario must qualify a real add/add conflict alongside
the existing modify/modify conflict after a 775,000-byte purpose. Each added
side carries over 90,000 bytes of complete ordinary UTF-8 text; the resolution
retains both sides and exceeds 128 KiB. The fixture checks actual stage sets,
present and absent bases, v2 round trip, all source and worktree text, exact
per-path proposals, both complete actual parent diffs and normal native
commit/push/fetch convergence. Each complete parent diff is a separate stdout
capture below its finite 1 MiB default stream budget. The common I/O default
does not constrain their aggregate size; aggregate resource guards remain
separately owned by CNCF. Repeated collection checks
native tips, index, merge state and history without replaying effects. Narrow
real-repository deletion, symlink-mode and binary scenarios retain refusal before
conflict work or materialization and preserve the pending native state.

`NativeRepositorySyncMaintenanceCliSpec` is excluded from discovery with
`@DoNotDiscover`. Select it explicitly only after publication, with
`smworkflow.spec.installedCommand` naming the exact absolute executable. All
business calls use that normal installed command through `NativeWorkflowCliFixture`,
with the scenario's explicit assembly descriptor and the published catalog's
normal `org.simplemodeling.textus.SmWorkflow:newest` selection. This qualifies
the installed command's ordinary published-catalog behavior; it does not pin
an immutable image through a runtime-root property.
The spec neither copies the application source tree nor publishes an image.
Its installed result is separate from prepublication direct-operation evidence.
The explicitly selected installed case must qualify the same mixed large-text
conflicts and optional-base readback through the installed command, preserving
the existing same-Session purpose, independent review, convergence and passive
collection checks. These are qualification requirements, not execution claims.
Its combined public review JSON is one file input larger than 1 MiB, so this
isolated installed host declares `cncf.resource.read.max-bytes=2097152` and
checks that file remains below 2 MiB before evidence preparation. Each Git
stdout retains its 1 MiB budget; the common default is not an aggregate cap.

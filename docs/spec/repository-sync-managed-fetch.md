## Public contract and authority

The generated `RepositorySyncWorkflow` revision is explicitly
`repository-sync-managed-fetch-v2`. Existing stored v1 definition bindings are
not silently migrated. The additive trusted host assembly exposes
`RepositorySyncService.startRepositorySync` and `advanceRepositorySync` together.
Advance accepts only the saved instance identity; the client chooses no stage,
Git argument vector, endpoint, executable or receipt. Generated legacy stage
operations remain declared, but are not installed by this two-operation assembly.

Start requires the actual authenticated original participant, a call-scoped host
selection with complete typed input, and the fixed host repository/tracking
mapping. Native instance identity uses the explicit selection and invocation
references, not a content hash. Repeated Start consumes its saved native entry;
it is not a new allocation or an adapter to legacy fixture receipts.

All durable stages use `WorkflowComponentStorage` through the owning component,
canonical DataStoreSpace and the single Subsystem-managed physical pool. The
assembly captures declarations and a selection reader, not a provider, driver
or lease. Git effects use the existing scoped ProcessExec/UoW interpreter and
host-fixed capabilities; no component ProcessBuilder or direct SQLite is added.

## Native progression and external-effect recovery

The owning call moves `sync.BoundaryAssessment` to CML-declared `sync.Fetching`
with a persisted mechanical intent. That intent records the original selection,
actual selected root/branch, local HEAD/tree/dirty status and the actually
advertised upstream tip. These are effect preconditions and native Git facts,
not a certificate that source files or intermediate records stayed unchanged.

The host defines fixed worktree-root and selected-remote-tip observations in
addition to the programs described in [managed Git observations](repository-sync-managed-git-observation.md).
Before the fetch, the workflow checks its actual root/branch/local Git facts.
It then performs at most the selected fixed non-force fetch for a fresh intent.
The observed tracking tip must equal the advertised intent and have actual
left/right counts and one actual common ancestor before a fetched receipt is
persisted at `sync.FetchAdmitted`. Unrelated histories or unsupported multiple
ancestors fail before any automatic integration. Fetched payload admission now
requires that native ancestor; older incomplete payloads are not silently given
an invented ancestor or upgraded to success.

For a retained intent, an already observed expected tip permits recording the
effect without another fetch. If the prior effect is unestablished, the call
refuses automatic replay; resolution of that uncertainty is unfinished. If the
external effect ran but acknowledgement was interrupted, a later call can
observe the real tip and finish this stage. Fetch, acknowledgement and DB
commits are separate effects, not an atomic Git/database transaction or proof
of recovery from a real process crash.

A saved fetched receipt is returned without refetch. Its public response is
typed WAIT and actual relation, explicitly not final convergence. Clean merge,
dirty-material preservation before integration, conflict work/Human resolution,
validation/review and non-force push still need owning progression. A Step or
fetch receipt cannot close the Phase.

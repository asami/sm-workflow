# Native RepositorySync validation and review applicability

Date: 2026-10-08. Existing Phase5 implementation correction; all changed cases
are UNVERIFIED. Historical successful runs do not validate these new inputs.
No new policy, approval, repair frame or counter is introduced.

## R1 — Selected execution facts, not a policy declaration certificate

Native validation state stores mode, original reason, selected fixed check
bindings, actual source revision and receipts. It stores no complete policy or
policy identity/revision witness. Repository progress v3 writes these facts.
Its v1 reader extracts the actual mode/reason/check plan from the former policy
container and ignores its absent or unusable identity/revision metadata. It
does not recreate a Policy, compare a declaration, rewrite a row or invent a
check result/permission. The v2 reader consumes its already selected facts.
Missing actual old check facts remain an explicit error.
New-format fields cannot reintroduce the removed policy witness. Readers admit
declared nested structure and actual types, not a re-encoded body certificate.

Recovery consumes the original selected check plan and reason. Current host
bindings must resolve the selected check identity/ordinal and the skip/required
mode must remain semantically compatible. A different policy name/revision/
explanation, declaration ordering or extra unselected binding is not a refusal
or reason to execute another check. Missing/replaced selected bindings and an
incompatible product-test skip/required mode are real incompatibilities, not
metadata stability checks. The ordinary runtime still admits each actual fixed
program and its current execution permission; AI cannot supply commands.

Validation matches actual native candidate/index/parents/tracking and selected
source frontier, not a complete copied observation or earlier history.
Completed validation admission is shared with nonmerge convergence selection,
including real receipt coverage and success. Actual worktree conditions, state,
CAS, scope, permission, failure/indeterminate outcomes and unknown-effect
non-replay remain. Separate Git observations are not an atomic snapshot.

E1: RepositorySyncNativeValidationApplicabilitySpec checks v3 selected facts,
legacy v1 policy extraction with ignored metadata and actual malformed/missing/
undeclared check data. This is codec coverage, not historical-store migration.
E2: it distinguishes policy metadata/extra bindings from absent/replaced selected
bindings or a semantically different mode. This is binding selection, not a
complete managed execution test.
E3: RepositorySyncManagedFetchSpec physically reopens successful merge validation
with different policy metadata and does not replay checks or relabel old meaning.
E4: physical reopen refuses an incompatible mode or missing selected binding
without executing checks or pushing.
E8: prepared/executed/recorded check acknowledgement reopen accepts changed
metadata and an extra unselected binding; it keeps the original plan, executes
only genuinely unstarted remaining checks after a recorded result, and never
replays an unknown effect. These physical cases use current v3 progress rows, not all
historical formats or separate-JVM production-provider evidence.
E9: RepositorySyncNativeValidationApplicabilitySpec exercises actual adjacent
native frontiers and selected receipt coverage despite observation diagnostics;
missing/failed results, another source or a result for another assigned check
refuse. This selector case is not a physical full validation/effect run.

## R2 — Consume the original independently assigned review

CML and application review Request remove validation/review policy identity and
revision fields. Request v2 omits them; v1 reads discard their arbitrary obsolete
values without a new metadata gate or renewed authority. Actual validation mode,
original rationale, selected check identities/results and complete semantic
candidate coverage remain review inputs. Required operation/type/route discovery
remains unchanged; normal generation is required, not manual generated edits.

Review preparation resolves actual instance/validated revision/parent/index/check
targets. It does not compare copied policy explanations or full receipt bodies.
The actual saved issue supplies its original meaning, Context, requirement and
presentation rather than being compared with a projected complete WorkOrder.
Current run/Continuation/revision/Required route/types/contracts/model scope and
independent-review requirement still resolve. Current coverage limits and real
pending repository changes still matter; policy identity/revision is not an
unchanged-content certificate.

Suspension delegates atomic admission/readback to its managed owner, rather than
pre-admitting the same SuspensionIntent and then loading a copied issue to prove
full equality. Completion computes the semantic successor once and uses its
actual committed InstanceRecord for response, without reloading a Result solely
to compare the submitted body. Actual correlated closing result and resulting
state remain required. Accepted review is not effect permission or a substitute
for separately admitted independent evidence. No independent AI review is
claimed from test fixture enrollment.

E5: RepositorySyncNativeValidationApplicabilitySpec covers omitted new markers,
legacy discarded values, structured Request/Result reads and actual malformed/
unknown/coverage errors without full-body re-encoding.
E6: it selects original issued meaning/presentation despite new projections and
refuses another slot/revision/route or removal of independent review requirement.
Actual candidate correlation is additionally owned by the paired native source
preparation; this selector-only case is not complete review admission.
E7: RepositorySyncManagedFetchSpec physically reopens original clean/conflicted
merge review after changed validation and review metadata, returns the original
issue, completes through independently enrolled fixture evidence and does not
recapture diffs or replay checks. Existing foreign reviewer/slot/path, missing
evidence, real pending edit, failed validation and duplicate completion cases
remain. Current review request rows use v2 and progress rows use v3; legacy codec
cases do not prove all store formats.

## R3 — One original Start, not downstream command-copy certificates

Managed Start retains the actual typed selected command in its existing public
v1 command wire. Start/fetch storage v2 emits it only for Start; fetch rows store
actual intent/observation/effect facts, not another command. Native progress v3
has no originalCommand member. Legacy fetch v1 and progress v1/v2 readers discard
the obsolete copy even when missing, null or unusable; they do not reconstruct
authority, rewrite a row or replace the real Start. New rows cannot reintroduce
that removed field. Start still requires its real typed command; actual progress
data, supported formats and declared nested types remain required.

A fresh Start consumes actual call-scoped Human selection and resolves repository,
branch, tracking remote/branch, endpoint and synchronization mode. It does not
compare the selected JSON and host declaration as complete bodies or require
matching repositoryPolicyVersion metadata. A repeated Start selects the saved
original invocation, participant and target; it does not renew Human selection
solely to certify unchanged input. The actual saved Start remains authoritative;
request/installation metadata changes never relabel it. The legacy policy-version
field is still required by the public typed input/adapter; its global removal is
not claimed here. An existing Start is not fresh permission for an external effect.

Native advance admits its original session once and consumes the fetch adapter's
actual result directly, rather than encoding a response, reloading it and comparing
copies. Current progression must include the selected fetch frontier, not remain
equal to that earlier state. Native convergence uses the original typed command
resolved from Start, not a downstream copy. Actual state/CAS, participant, target,
Git preconditions/postimages, current effect permission and unknown-effect
non-replay still apply. Separate Git observations do not become atomic snapshots.

E10: RepositorySyncNativeValidationApplicabilitySpec covers the original Start
wire, omitted fetch command copies, legacy discarded absent/unusable copies,
actual missing/foreign typed fields and invocation/participant/target differences.
E11: it covers progress v3 output and v1/v2 ignored command copies, retaining
actual required state fields. These are codec/selector cases, not historical
physical-store migration or complete permission admission.
E12: RepositorySyncManagedFetchSpec physically starts/reopens with different
host/request policy metadata, keeps the original selected command and current
instance, and does not replay fetch. Fresh Human selection is still enrolled by
the fixture; it is not proof of new production consent or model execution.
E13: physical nonmerge reopen with different policy metadata and a currently
successful program retains the original failed result, without check/push replay.
E14: physical nonmerge validation reopen with different declaration/policy
metadata completes through current fixture effect authority, without replaying
checks or creating a merge commit; only genuinely pending push/final fetch run.
Repeated advance preserves Terminal without replay. Physical cases use current
rows, not every historical format or deployed provider. All remain UNVERIFIED.

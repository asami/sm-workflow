# RepositorySync formal failed-check continuation

`describeRepositorySyncValidationContinuation --sessionId` supports the explicit
`sm-workflow.repository-sync-formal-failure-continuation.v1` policy for a genuine
retained failed product check on a Purpose candidate or a pending merge. The
existing resultless nonmerge v1 contract remains unchanged. This policy does not
introduce a nonmerge formal-failure FIX lifecycle.

The target retains the original check, full diagnostic receipt, successful
ordered prefix, intent/result and candidate references/revisions, native
frontier, selected validation policy and fixed Purpose workspace when applicable.
The original native rows and candidate remain immutable. Structural failure,
missing/resultless output, UNKNOWN termination, incomplete captures, changed
selection, candidate or source lineage are ineligible.

The target also binds the current ordinary resolved process-execution plan from
the call's ExecutionContext. CNCF interprets and executes that plan. The target
does not reconstruct a historical environment or claim that a configuration
difference was proven. No executable, command vector, language interpreter or
untyped process fallback is introduced.

The public Record projection carries each opaque `processPlan` object as its
complete JSON text string. This includes plans inside nested prior host
directions. Record field-name formatting and public schema-name normalization
therefore cannot change host-map keys such as `JAVA_HOME`, `HOME`, `PATH` or
mixed-case and punctuation keys. The text preserves all original keys, explicit
nulls, arrays, objects and values; sm-workflow does not interpret or normalize
the CNCF declaration inside it.

Target decoding restores those strings to their exact JSON objects before the
existing domain decoder, target validation and canonical equality check.
Malformed JSON text, scalar/array/null plans, null target fields and extra
target fields refuse. Internal encoding and historical stored object-shaped
plans remain unchanged and continue to decode directly. No target-equality
waiver or plan normalization is applied. An old unadopted public description
whose host keys were already changed by Record formatting must be described
again; its original arbitrary key spelling cannot be recovered from that
mangled object. This adds no operation or compatibility alias.

The choices are `AuthorizeNewValidationAfterHostCorrection` and `Defer`. The
existing public evidence-preparation operation binds the full target, Component,
participant, reference, choice, ordinary nonempty rationale and both lifecycle
assertions under `repository-sync-validation-continuation` evidence. If a repair
WorkOrder is pending, it must be actual, available, unclaimed and incomplete;
the adopting answer requires `priorExecutionEnded=true` and
`acceptOriginalUncertainty=true`. Those assertions concern the prior semantic
worker and its UNKNOWN external effects. The check itself remains formally
failed. Without a pending issue, both assertions are false and not applicable.
Absence of a claim is never evidence that a worker had no effects.

The explicit `sm-workflow.repository-sync-formal-failure-continuation.v2`
policy covers a failed Purpose whose retained original selection has no
`TestOnly`, when both the current fixed validation policy and current Purpose
slot register applicable `TestOnly` checks. Its required `proposedChecks` is
the unchanged original ordered batch followed by all applicable additions in
current policy order. Every addition has a new identity and the exact registered
ordinal/kind. Deletion, weakening, reordering, renaming, arbitrary tests, missing
or null proposals and use on a pending merge refuse. No applicable addition
means the existing v1 description remains in use; no registration is invented.

V2 offers `AuthorizeNewValidationAfterSelectionCorrection` and `Defer`, under
the same independent evidence purpose. V1 retains its original choices and
encoding, with no `proposedChecks` field. Each version rejects the other adopting
choice. Preparation checks the actual target's ordered choices; the evidence
binds the complete proposal, original failed selection, candidate, prefix,
current slot/workspaces and opaque resolved host plan. Typed CNCF SBT admission
continues to own program validity and execution permission.

Separate Advance copies the failed Purpose progress with `selection.checks`
set to the exact proposed batch, only its identical successful prefix receipts,
and the saved direction in a fresh existing host namespace. Grouping, candidate,
request, base, commits, slot and repair counters remain unchanged. Authentication
permits that transformed selection only against this actual retained direction.
Old original selection and receipt history remains readable after subsequent
failures and directions. Appended `TestOnly` requires an actual fresh invocation
and nonempty selected-test evidence; prior reusable receipts cannot replace it.
Normal independent review follows completed validation. Correcting PATH alone
or omitting selected tests supplies no candidate acceptance.

The existing adoption Operation accepts exactly one of optional `input` and
`inputResource`. The latter is an absolute local file URI containing the entire
normal adoption DTO, including every opaque `processPlan` string. Installed
Session routing and the native executing call use the same strict decoder and
normal CNCF Resource reader. Duplicate keys are checked before Record conversion;
null, unknown, missing, coerced and crossed fields refuse before evidence
admission or effects. Both/neither refuse without a fallback. CNCF owns roots,
finite byte limits and strict UTF-8 acquisition; sm-workflow imposes no byte cap
and never truncates or rebuilds the supplied business data.

Adoption supersedes the exact pending native WorkOrder through
WorkflowManagedWorkOrderSupersession, or appends a mechanical direction when no
issue exists. It records `FormalFailureContinuationAdmitted` without checks,
staging, candidate changes, commits or publication. An identical repeat at that
frontier is observable; stale or contradictory repeats refuse. Defer is passive.

A separate `advanceRepositorySync --sessionId` authenticates retained direction,
source lineage, current candidate, host plan and selected policy. Purpose
progress retains the same repair attempt, group cursor, slot, candidate and
commits, with a separate `-host-<frontier-revision>` attempt suffix. Pending merges
receive a `formal-failure-<frontier-revision>` namespace with an authenticated
link to the unchanged original candidate. Only the successful prefix is seeded;
the old failed row is excluded from the new attempt and stays readable.

Normal Advance saves the next intent before ordinary typed SBT execution. A
resultless new intent is not replayed. A new genuine failure returns to ordinary
FIX handling; later checks, assessment, review and convergence retain their
normal owners. A later host correction may describe that new failed result
without resetting repair counters or imposing a host-attempt cap.

Authored evidence:

- `RepositorySyncFormalFailureContinuationSpec`: full diagnostics, Purpose/merge
  targets, successful prefixes, strict discrimination and exact host bindings;
  the public Record serialization/normalization/decoding path preserves opaque
  host plans and nested prior directions, with malformed-plan refusals.
- `RepositorySyncPurposeRuntimeSpec`: independent attempt keys, historical
  defaults and unchanged repair/cursor/slot/candidate/commit accounting.
- `NativeRepositoryFormalFailureContinuationCliSpec`: tiny real product
  repositories, actual SBT launcher failure under an isolated invalid JVM launch option,
  public describe/preparation/adoption, host drift refusal, old Submit rejection,
  separate Advance and successful-prefix preservation on Purpose and merge routes.
- `NativeRepositoryValidationSelectionCorrectionCliSpec`: explicitly selected
  installed tiny Purpose fixture with an actual failed SBT receipt, pending old
  worker UNKNOWN supersession, exact v2 adoption, real nonempty TestOnly and
  normal independent review after separate Advance.
- `NativeRepositoryValidationResourceContinuationCliSpec`: the same tiny product
  with normally configured complete host registrations yielding a target larger
  than 4,653,720 UTF-8 bytes, strict Resource refusals, faithful passive adoption,
  complete opaque-plan retention and exactly one subsequent selected-test run.

The two new installed suites are `@DoNotDiscover` runtime specifications and
require the actual installed command plus ordinary SBT executable. They create
their own tiny Git roots and SQLite Sessions and never copy a consumer repository
or database. Fixture host registrations are configured before description;
described target content is never padded or truncated.

These are authored specifications. Generation, compilation and execution results
belong to the parent verification workflow.

The CLI suite also supports retained installed upgrade episodes. Select
`smworkflow.spec.formalFailureEpisodeStage=before` and an existing absolute
`smworkflow.spec.formalFailureEpisodeDirectory`, together with the old
`smworkflow.spec.installedCommand`. This creates the tiny Purpose and merge
failures and saves `purpose.json` and `merge.json` containing only fixture
root/Session, public host/plan metadata and actual stdout. It does not call the
new description/adoption operations. After publication, select the same directory,
`formalFailureEpisodeStage=after` and the new installed command. The suite uses
`NativeWorkflowCliFixture.reopenInstalledRepository` to continue those actual
roots and Sessions without rerunning successful checks or editing native rows.
With no episode-stage property it exercises fresh normal sessions.

## Failed Purpose baseline repair inventory

A genuine exited nonzero selected Purpose check can require an existing baseline
test outside the current group's changed files. The existing
`describeRepositorySyncRepairScopeCorrection`,
`prepareRepositorySyncRepairScopeCorrection` and
`adoptRepositorySyncRepairScopeCorrection` operations support this case under
`sm-workflow.repository-sync-repair-scope-correction.v4`. This is an inventory
correction for the actual pending native repair WorkOrder. It does not authorize
another validation attempt on an unchanged candidate through the formal-failure
host or selection direction described above.

The v4 target binds the actual failed Purpose stage, its earlier native prepared
candidate receipt, the original available unclaimed incomplete repair issue and
its exact frontier, and the entire retained Purpose progress. This includes the
original request and source records, ordered plan and ownership, cursor, attempt,
slot, candidate, receipts, effects and commits. The failed virtual candidate tree
is distinct from the original repository index tree. Both review tips are the
candidate parent; no pending merge or divergent tracking relation is required.
Historical v1-v3 targets and checkpoints retain their original contracts and
canonical representation. The new optional Purpose field is omitted when absent;
explicit null, unknown or malformed Purpose fields refuse.

Preparation qualifies sorted safe existing regular tracked ordinary UTF-8 files
from that exact candidate using typed Git TreeEntries and BlobContent. It retains
their actual blob identities and the complete progress and original repository
snapshot under the distinct
`sm-workflow.repository-sync-purpose-repair-inventory.v1` policy. Added unchanged
baseline files must have the same real original worktree text as the candidate
blob. The original HEAD, branch, index, captured inventory worktree texts, selected
clean validation slot and absence of merge/unmerged state are revalidated.
Candidate or source drift refuses while preserving bytes. File count creates no
Human eligibility gate.

A v4 newly added path owned by a later planned Purpose returns a concrete conflict
naming the path and that later group before supersession or effects. Later text
is never substituted for candidate text. Existing shared paths already belonging
to the current group keep ordinary repair behavior. This contract selects the
explicit conflict alternative. Existing v4 targets retain that refusal; v5 below
provides a separately qualified ownership assignment without implicit text merging.

Prepared scope is fixed. Independent prior-worker lifecycle evidence uses the
existing `ContinueAfterPriorWorkerEndedAcceptingUnknown` choice and both explicit
terminal and UNKNOWN assertions. Read-only describe/prepare and adoption do not
run checks, edit files or prepare a new candidate. Adoption uses existing atomic
native WorkOrder supersession. An identical adoption is idempotent; stale,
foreign, contradictory and crossed contracts refuse. Separate ordinary Advance
captures the exact qualified candidate text into the successor request, retaining
the old issue and receipts.

Normal repair submission changes only the assigned files. Ordinary continuation
adds corrected extra files to the current group's content and appends their
captured original worktree baselines to the request inventory. Existing current
paths are preserved, and original request fields, source records, other groups,
dependencies and exclusions remain unchanged. The next repair attempt advances
the existing attempt and slot counters and uses the failed candidate tree as its
baseline. Candidate/check selection is cleared for ordinary candidate preparation,
fresh affected checks, independent review and actual Purpose commit. Historical
failures, successful receipts, commits, effects and UNKNOWN remain retained.

`RepositorySyncRepairScopeCorrectionSpec` and `RepositorySyncPurposeRuntimeSpec`
cover canonical compatibility, exact progress binding, malformed/drift refusals,
added candidate propagation, preserved ownership and the named overlap conflict.
`NativeRepositoryPurposeRepairScopeCorrectionCliSpec` is a `@DoNotDiscover`
`RuntimeTestDeclaration` with exactly one registered test per selected phase:

- Before producer publication, set
  `smworkflow.spec.purposeRepairPhase=capture` and
  `smworkflow.spec.purposeRepairEpisode=<absolute episodeJSON>`, plus the actual
  old `smworkflow.spec.installedCommand` (or its existing environment equivalent)
  and normal `smworkflow.spec.sbt` / `SM_WORKFLOW_SPEC_SBT`. The test
  `capture legacy failed purpose repair` creates only a tiny fixture repository,
  obtains successful Compile and a genuine stale-baseline Test assertion failure,
  and retains the actual Session, repository, host, plan, original work, receipts,
  logs and old describe 409. Invalid host configuration is not the failure.
- After ordinary producer publication, set `purposeRepairPhase=continue` and the
  same episode file with the new installed command. The test
  `continue retained failed purpose repair` reopens the same physical repository
  and datastore, proves the concrete later-owner conflict and nondestructive
  refusals, supplies fixture-authored lifecycle evidence through normal
  prepareEvidence, adopts once, issues corrected work through separate Advance,
  submits the real baseline correction, obtains fresh checks and independent
  fixture reviews, and finishes both original Purpose groups and the original
  Session using its fixture-local bare remote. It retains machine-readable
  `<episodeJSON>.result.json` evidence. It never copies a consumer repository,
  edits native database rows or claims live Human/reviewer acceptance.
- For an isolated fixture continuation after the baseline repair proposal was
  accepted and the first grouped Advance failed, set `purposeRepairPhase=finish`
  with the same episode file and repaired installed command. The test
  `finish retained accepted purpose repair` requires that same Session to remain
  exactly at `sync.RepairProposalAdmitted`, with its original work and failed
  checks retained. It resumes only the common tail beginning with grouped
  Advance, then obtains fresh affected checks, fixture reviews, both local
  Purpose commits and the terminal result. It preserves the failed installed
  qualification and successful prefix without repeating capture, qualification,
  adoption, repair submission or prior successful checks. Its same
  `<episodeJSON>.result.json` is created only once and identifies the resumed
  accepted repair and retained installed failure through qualification metadata;
  it does not claim to have rerun target or overlap qualification. This phase is
  fixture-only and performs no direct native datastore mutation.
- For the one separately authorized normal-completion control, set
  `purposeRepairPhase=completion`, select a new absent
  `smworkflow.spec.purposeRepairEpisode` destination, and supply the retained
  original episode separately through
  `smworkflow.spec.purposeRepairOriginalEpisode`. The test
  `complete one isolated current-installed purpose repair control` checks that
  the new episode and result paths are absent before creating one tiny repository
  and Session. Its initial host declares Compile, Test and fixed nonempty
  TestOnly checks for all three slots, selecting the authored
  `fixture.BaselineSpec` and `fixture.FutureSpec` classes. Shared capture,
  continuation and completion helpers obtain a genuine baseline Test failure,
  qualify the scope, adopt once, submit the correction, obtain fresh successful
  checks including actual selected TestOnly suites, and require both local
  Purpose commits and Terminal in that same new control Session. Episode and
  result evidence use CREATE_NEW; there is no automatic replacement or retry.
  Provenance identifies a current-installed normal-completion control and its
  initial describe preparation-required result, rather than an old-product 409.

The actual retained old-to-new episode remains nonterminal: its qualification,
scope adoption, accepted correction, grouped transition and fresh Compile/Test
successes remain evidence, while subsequent code admission stopped because that
fixture's initial host lacked a fixed TestOnly selection. The separately selected
completion control does not alter or replay that episode, replace its logs, or
claim that the old episode reached Terminal. Its execution result is separate
evidence from the retained old-to-new qualification.

These specifications describe the required qualification; execution and actual
results belong to the owning parent workflow.

## Failed Purpose repair with later ownership

The distinct `sm-workflow.repository-sync-repair-scope-correction.v5` target and
`sm-workflow.repository-sync-purpose-repair-inventory.v2` qualify an existing
failed candidate file also owned by a later planned Purpose. The same public
prepare, describe and adoption operations retain their lifecycle roles. The
target binds the exact failed progress, original request and later groups,
candidate baseline blobs, captured original worktree, native WorkOrder and
repository facts. Original later text can differ from the failed candidate;
qualification checks it against the captured ownership facts, rather than
requiring that later intent already equal the candidate. Unsafe paths,
unexamined text, invalid ownership, candidate drift and root drift still refuse
without changes. Nonoverlapping v4 and historical contracts retain their
representations and behavior.

Following fixture-authored or actual independent lifecycle evidence and native
supersession, separate ordinary Advance issues the existing nativeRepair work.
Its outer `purposeWork` records expose the candidate baseline, every affected
later owner's complete original group, effective group, original files,
captured worktree and exact required identity/path pairs. Current candidate
repair text and later integrated text are separate decisions. A repaired result
must provide the normal current `replacements` plus `purposeContinuation` with
every assigned pair and complete integrated ordinary text, with a causal
rationale. Missing, extra or crossed ownership cannot silently consume another
Purpose's intent. No new repair engine, fallback, file-count gate or lifecycle
consent is introduced.

Purpose progress retains its original captured request and exact later plan
groups. The explicit `ownership` continuation stores integrated later text
separately. An effective later group overlays only its assigned paths; unrelated
content, dependencies, exclusions and messages keep their original ownership.
The repaired current group contains the current correction alone. Its ordinary
checks, review and actual commit occur before the later Purpose's separate
checks, review and commit. Installation records the actual `projectedWorktree`
as the expected remaining root content. Consequently the original stale
baseline cannot overwrite the accepted current correction when later intended
work is restored. Original failure/UNKNOWN history, counter lineage and native
receipts remain evidence; adoption is not candidate acceptance.

If the meanings conflict, the worker returns `decision-needed` with a precise
actual path and owner rationale, empty replacements and no continuation. The
existing public route retains that decision and returns `Wait` with condition
`RepairDecisionRequired`, requiring actual semantic/Human resolution. Repeated
Advance runs no candidate, checks or commits. This contract provides no invented
follow-up API, automatic Human answer or silent overwrite and does not claim
that such a Session is resolved.

The existing installed fixture adds two explicitly selected ID07 phases using
the distinct absolute `smworkflow.spec.purposeOwnershipEpisode` property:

- `smworkflow.spec.purposeRepairPhase=ownership-capture` runs against the actual
  old installed product before publication. One test authors two tiny local Git
  repositories and local bare remotes: a stale baseline later extended by a
  distinct comment, and a stale baseline with a genuinely conflicting later
  expected value. Every used slot initially declares Compile, Test and fixed
  nonempty TestOnly selections. Each first candidate obtains real Compile
  success and a genuine baseline Test assertion failure. Actual prepare 409
  logs name the baseline path and later owner, and the unchanged full Session,
  progress, request, formal receipts and root snapshot are saved. The wrapper,
  `.resolved.json`, `.decision.json` and result destinations must be absent;
  episode writes use CREATE_NEW.
- `smworkflow.spec.purposeRepairPhase=ownership-continue` reopens those exact
  saved Sessions using the new normally installed product after publication.
  It proves v5 qualification, passive repetition, invalid path/drift/lifecycle
  refusals, original worker refusal and truthful ownership work. The conflicting
  Session submits its actual unresolved decision and proves nondestructive
  repeated Wait. The resolvable Session submits current baseline correction
  separately from later correction plus comment, then requires grouped progress,
  fresh actual checks, clearly fixture-authored independent review evidence,
  current commit and integrated root projection, later candidate checks/review
  and commit, and clean converged Terminal. Repeated Terminal must cause no
  extra process. Its CREATE_NEW result includes actual commits, retained
  failure/UNKNOWN evidence, receipts, assignment, final tree and unresolved
  decision evidence. No previous successful case is replayed.

The four ID06 selectors, retained episodes and results remain separate. These
are authored requirements; only the owning parent's normal generation,
compilation, old capture, publication and same-Session installed continuation
provide execution evidence. The fixture does not inspect or modify a live
consumer Session and never writes native datastore rows.

## ID08: known failed first-Purpose preparation

`describeRepositorySyncPurposePreparationContinuation --sessionId` observes the
actual current `PurposeUnfinished` native receipt and its directly preceding
immutable intent. The caller supplies no native receipt key and reads no private
storage. Its target retains the complete failed progress JSON and complete real
provider effect JSON as opaque strings. Journal payload names, arrays, explicit
nulls, old effects and accepted ownership text survive public Record conversion.
The process observation includes the original stdout, stderr, byte counts,
truncation flags and termination; an unavailable or incomplete result is never
replaced by a fabricated failure.

Only the first ordered Purpose repair is eligible: cursor zero, no installed
Purpose commits, positive existing repair attempt, defined baseline tree, no
candidate, intact original plan and accepted ownership. The actual paired intent
must be `PurposePreparing`, with a `Failed(nonzero)` result and matching exited
nonzero process termination, complete untruncated streams and no pending merge.
The actual source HEAD, index, branch, root mapping, retained endpoint/principal
and every selected expected worktree text must remain applicable. Drift and
unknown, truncated, materialization or commit results retain their actual receipt
but offer only `Defer`. This contract does not authorize arbitrary later-Purpose
or uncertain installation failures.

`adoptRepositorySyncPurposePreparationContinuation` accepts typed `input` or
`inputResource`: sessionId, the exact described target, choice, ordinary nonempty
Unicode rationale, directionReference and matching executionEvidence. The choices
are `AuthorizeNewPreparation` and passive `Defer`; rationale has no application
size limit. The independent evidence purpose is
`repository-sync-purpose-preparation-continuation`. Passive preparation uses
family `RepositorySync`, kind `purpose-preparation-continuation` and the exact
DescriptionResult plus Answer. Supplied external reference, participant, worker,
issuer and time are encoded, not manufactured or interpreted as proven Human
approval. No `priorWorkerEnded` assertion substitutes for the actual stored
process termination.

Adoption re-observes the exact current facts and appends one managed mechanical
`purpose-preparation-continuation` event from `PurposeUnfinished` to
`PurposeGrouped`. Progress changes only its optional `preparationNamespace` to
`prepare-continuation-<failed-frontier-revision>`; the payload additionally retains
the exact direction. The adoption receipt key is that namespace plus `-adopted`.
The accepted repair, prior UNKNOWN effects, immutable failed intent/result,
request, plan, ownership, effects, cursor, attempt, slot and repair accounting
remain unchanged. Identical repeated adoption collects the same receipt; crossed,
stale or contradictory directions refuse. Adoption executes no Git, SBT,
validation, Submit, Start, commit or push.

Separate ordinary Advance authenticates the immutable adoption and original
paired failure again, checks actual source applicability and writes one new
preparation intent under the distinct namespace. The old prepare keys are never
overwritten. A new unknown effect is retained without automatic replay. The
namespace and direction do not authorize another repair attempt or subsequent
Purpose; normal candidate verification, validation, independent review, commit
and terminal handling remain authoritative.

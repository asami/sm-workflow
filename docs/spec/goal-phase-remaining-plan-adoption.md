# Explicit adoption of a remaining Plan

date=2026-10-20
status=implemented-local-installed-route-qualified

This boundary addresses the human-selected Phase 12 policy at the existing
Phase 6.4 frontier. It does not replace the ordinary bounded
[Plan revision](goal-phase-plan-revision.md) guards, answer a historical question,
or reopen an accepted Step. The explicit user instruction was verified in the
architecture chat; the host must still admit the actual directive and its
selected business target through its independent evidence provider.

## Selected design

Provide a read-only description of the actual same-Session semantic Decision,
its pending issued question, current complete Plan, selected documents, accepted
prefix and repair progress. A separate typed adoption operation consumes a raw
complete replacement Plan, the exact described target and the actual independently
host-admitted Human directive reference. The implemented operations are `GoalPhaseService.describeGoalPhaseRemainingPlan`
and `GoalPhaseService.adoptGoalPhaseRemainingPlan`. Description input is
`GoalPhaseRemainingPlanDescriptionInput(sessionId, proposal)`; the required
proposal captures the actual future contract and selected File-owned documents.
Adoption input is `GoalPhaseRemainingPlanAdoptionInput(sessionId, target,
proposal, rationale, reference)`. Copy the returned target unchanged. The
independently admitted directive binds that exact target and rationale.

The host may interpret the already supplied user instruction for this exact
remaining-work change. It must not ask for the same design choice again, invent
an answer to the old question, or turn this Markdown into a consent reference.
The directive is new adoption input with its own provenance; it is neither
`ApproveDependencyScope` nor a replay of `submitGoalPhaseOrderedDecision`.

## Eligibility and immutable history

- The actual current frontier is a semantic Decision with a genuinely issued,
  unanswered question, sourced from implementation or repair. No unknown native
  effect, exhausted repair window, closure intent, document conflict, accepted
  Phase review or Closed state is eligible.
- Session identity, original base, Plan identity/Phase/repository, Step count and
  order, every Step ID, owned paths, dependencies and work classification remain.
  Repair limit and selected Phase check/review policy remain unchanged. Current
  and cumulative repair counts, issue/finding history and actual prior results
  remain; generation increments once.
- Every accepted Step definition, commit and review reference remains exact.
  Its historical Plan, effective acceptance and document wording remain in the
  original retained native requests/results. Adoption does not claim that the
  old Step passed the new contract.
- Only current and future unaccepted Step purpose/checks may change. Their
  selected checks must already be declared by the host; adoption grants no
  executable, target, workspace, file or permission capability.
- The newly captured Usage Contract and conditions apply only to new work and
  future Phase acceptance. The old accepted contract remains historical, not
  silently rewritten. Existing ordinary `adoptRevisionC`/refresh guards stay.
- Document source, Step-to-item membership, item IDs and checked flags remain.
  Accepted-prefix items remain exact; acceptance text may change only for
  unchecked remaining items. The actual File owner loads the selected documents;
  a stored Plan or private database is never edited.

## Actual native transition

The operation admits the directive and proposed suffix together, then appends a
normal managed native transition with the actual pending revision as predecessor.
Its retained business result records the old question identity and an explicit
`superseded-by-adoption` disposition, the actual directive reference and selected
new Plan/documents. It does not manufacture a completion answer for the old
question or delete its issued record. Only the native history walker consumes
this disposition and resumes the same Step at Implementation with fresh semantic
work, candidate inspection, checks and independent review still owed.

The old question is no longer an actionable frontier. A stale answer, duplicate
adoption or concurrent submission must fail through the native revision/claim
contract. If the transition outcome is unknown, observe its exact retained
association; do not replay it, recapture later defaults or reset state.

## Required verification and delivery

Use an isolated representative Session with accepted E1, an unanswered dependency
question, nonzero repair history and retained successful/failed results. Verify
read-only description, missing/mismatched independent evidence rejection,
successful same-Session adoption, exact old prefix/base/counter preservation,
document checks, stale-answer/duplicate rejection and ordinary continuation into
only the remaining work. Negative cases retain the existing global guards.

The live Phase 6.4 Session is not a fixture. Its consumer owner receives actual
generated interfaces, configuration, normal publication/deployment identities,
validated sequence and limits after delivery. Do not provide a speculative
operation as a usable workaround or claim this design as completed adoption.

## Delivered host procedure

Both operations and passive
`NativeHostPreparationService.prepareEvidence(kind=remaining-plan-adoption)`
are locally published and qualified through the normal installed CLI. The
[producer delivery](../journal/2026/10/2026-10-20-phase-12-producer-delivery.md)
describes actual description → independent host directive admission → ordinary
StartupImport → adoption → Advance. Passive preparation does not create consent
or grant authority. Fixture directive records are specification-owned and cannot
be imported as live Phase 6.4 Human provenance. Live adoption and Phase closure
remain separate from the installed qualification.

3. **D3 / P66-07..09:** Have AI propose one concrete cause/evidence/scope/test
   Fix Manifest; use the existing repair assignment and actual focused behavioral
   validation. Preserve earlier hypotheses/results when diagnosis changes. Do
   not create one worker per failed test or treat compilation alone as test success.
4. **D4 / P66-10..12:** Verify the connected path, update affected public and
   caller/skill contracts, deliver through normal packaging/deployment and record

The first acceptance path is failure → overview → one batched information round
trip → one repair → focused-test success → existing admission. An isolated
workflow can prove this connection without operating a live Session for a demo.

## Addendum: compilation failure and tests not executed

The user explicitly requires compilation-error diagnosis and repair within
Phase 6.6. The plan/specification and P66-13..15 now cover this branch without
renumbering or resetting P66-01..12.

SBT test and focused invocations may fail while compiling production or test
sources. Extract available project/configuration, compiler messages, source
file/line/column, surrounding source and type details. Through D2, AI can request
related declarations, call sites or generated/build context. AI distinguishes
root errors from cascading diagnostics and proposes a coherent repair unit;
there is no automatic worker per compiler message.

When compilation prevents a selected test from starting, record compilation
failure and **test not executed because compilation failed**. Do not report a
failed/canceled/passed test or successful empty test selection. Preserve tests
that actually executed in other parts of an aggregate invocation. If evidence
does not establish execution, retain unknown rather than guessing from exit code.

After repair, normal compilation must succeed and focused behavioral tests must
actually run. A compile-only PASS is insufficient. If those tests fail, continue
with their diagnostics in the same repair path, retaining the earlier compiler
failure, work history, repair counts and all applicable validation results.

P66-13 verifies compiler context and diagnosis; P66-14 verifies execution-state
classification; P66-15 verifies the repair-to-compile-to-focused connection. Use
one representative connected compiler-failure repair and proportional focused
fixtures for the other scope/mixed-result cases. This adds no separate engine,
per-read approval/review or mandatory repeated full suite.

This addendum changes documents only. Ongoing Phase 6.4/6.5 work, existing Sessions,
histories, repair counts and validation records remain unchanged; no tests were

# Phase 6.5 Candidate: Bad-Smell Triage and Deferred Finding Recording

Date: 2026-10-21
Status: Design candidate for review after Phase 6.4 baseline
Target: prospective sm-workflow Phase 6.5

## Context

Phase 6.4 is currently being exercised with the sm-workflow produced by Phase
6.3. The current workflow uses strong Step review/Admission. The preceding
workflow-optimization proposal considers removing mandatory detailed AI review
from ordinary Step closure while retaining deterministic validation, FIX and
re-validation.

This note refines that proposal. Rather than replacing Step review with no
semantic observation at all, use a cheap independent Bad Smell Detector as
triage. Detailed Review is started only when the detector or another explicit
workflow condition identifies a reason to investigate.

The motivation is not only model cost. Repeated detailed AI review at every Step
can create review-induced scope expansion: the reviewer keeps discovering local
improvements, speculative hardening or additional machinery, and REVIEW_FIX grows
the implementation beyond what the Plan needs.

## Proposed quality flow

```text
PLAN
  |
  +-- STEP
  |     implementation
  |       -> full compile + focused test
  |       -> Scala lint
  |       -> CAR lint
  |       -> deterministic FIX / affected re-validation as needed
  |       -> independent Bad Smell Detection
  |              |
  |              +-- CLEAN ---------------------> Step commit
  |              |
  |              +-- SUSPICIOUS / DECLINE
  |                         |
  |                         v
  |                   Detailed Review
  |                         |
  |                    findings / FIX
  |                         |
  |                   affected validation
  |                         |
  |                      Re-Review
  |                         |
  |                 repeat until converged
  |                         |
  |                         v
  |                     Step commit
  |
  +-- STEP ...
  |
  +-- RELEASE
        -> integrated/full validation
        -> Scala lint / CAR lint
        -> cbd-support Review
        -> comprehensive AI Review
        -> Detailed Review/FIX convergence where needed
        -> finalize accumulated nonblocking findings
        -> AI Final Recording
        -> Final
        -> release commit
```

## Bad Smell Detector

The detector is triage, not a reduced detailed review.

Its question is approximately:

> Does this Step contain a suspicious implementation/design signal that justifies
> starting a detailed semantic review?

It should not attempt to exhaustively prove correctness, enumerate every possible
improvement, or produce an implementation plan. A smell is a request for
investigation, not repair authority.

Representative smell families include:

- implementation size/complexity disproportionate to the Step purpose;
- duplicate state, duplicate validation or parallel mechanisms;
- speculative defensive/integrity/recovery machinery;
- unexpected responsibility or dependency-boundary expansion;
- UoW/managed-effect escape or architecture bypass;
- test-support concerns leaking into production machinery;
- abstraction growth without a corresponding Usage Contract need;
- repeated local checks that suggest the harness/model should own the concern.

The result should remain small and structured, for example CLEAN, SUSPICIOUS or
DECLINE plus attributable smell categories/evidence and a suggested review scope.

A SUSPICIOUS result starts Detailed Review. DECLINE is a normal escalation result,
not permission to call the Step clean.


### Deterministic lint smell detection and AI input contract

Scala lint and CAR lint are themselves Bad Smell Detectors for smells that can be
recognized deterministically or heuristically without semantic AI judgment. They
should emit ordinary errors/warnings and attributable smell signals where the rule
is appropriate. A smell signal is not automatically a product failure or repair
authority; it may be evidence that Detailed Review is warranted.

The AI Bad Smell Detector always receives the Scala lint and CAR lint results as
first-class input, including the explicit result that either lint found zero smell
signals. Do not invoke AI only for lint-positive Steps. Lint covers known/mechanical
smells; AI triage covers semantic smells, combinations of weak signals and
implementation shapes that are suspicious relative to the Step purpose even when
all deterministic smell rules are quiet.

The normal input bundle is therefore:

```text
Step purpose / acceptance boundary
  + candidate change/diff summary
  + compile result
  + focused-test result
  + complete Scala-lint result (including zero smells)
  + complete CAR-lint result (including zero smells)
        |
        v
AI Bad Smell Detector
        |
        +-- CLEAN
        +-- SUSPICIOUS -> Detailed Review with lint + AI evidence
        +-- DECLINE    -> escalation
```

When Detailed Review is selected, pass both the underlying lint evidence and the
AI smell assessment/review focus so that the stronger reviewer does not need to
rediscover why escalation occurred. This is evidence flow, not a second lint run.

## Independent context and model tier

Bad Smell Detection should normally run in a context separate from the
implementation worker. Context separation is useful here because the detector is
intended to provide an independent second look rather than continue implementation
reasoning.

This makes the detector a candidate for a cheaper model:

- first evaluate whether Luna can perform the triage reliably;
- if Luna is adequate, evaluate Local LLMs against the same task/corpus;
- SUSPICIOUS/DECLINE escalates to a stronger Detailed Reviewer.

Luna is the useful lower-bound control before Local LLM adoption. If Luna cannot
reliably perform this bounded triage, Local LLM use should not be assumed viable.

Implementation routing is a separate concern. Do not split Steps unnaturally merely
to fit a cheap implementation model. The default implementation worker remains
the capable Sol 6.1 High class unless later evidence supports another routing.
Small fixes inside a Step stay in that Step worker/context rather than spawning a
subagent whose context/setup cost exceeds the work.

## Detailed Review is a convergence action

Detailed Review includes its own repair loop; it is not one read-only review call.

```text
Detailed Review
  -> blocking/in-boundary findings
  -> REVIEW_FIX
  -> affected compile/test/lint
  -> Re-Review
  -> repeat until acceptance boundary converges
```

Convergence means required in-boundary findings are resolved and required
validation passes. It does **not** mean the reviewer can no longer imagine an
improvement.

Nonblocking improvements must not keep the Detailed Review loop alive. They become
pending Hygiene/Development Candidate findings for Release-time disposition.

Existing repair/convergence guards remain applicable. Failure to converge can
escalate to Human/replan/stronger reasoning rather than expanding scope indefinitely.

## Finding management

sm-workflow owns the lifecycle and identity of findings, not the prose editing of
Hygiene/Development Candidate documents.

During Steps, retain nonblocking findings as structured pending findings. Do not
launch an AI recording task after every Step or every finding.

Conceptually:

```text
STEP 1 findings --+
STEP 2 hygiene ----+--> sm-workflow pending findings
STEP 3 candidate --+             |
                                  v
                               RELEASE
                                  |
                                  v
                         AI Final Recording
```

The retained record should be sufficient to preserve identity, source Step/review,
category/disposition, evidence/reference and current resolution state without
creating a second content snapshot or management ledger.

Blocking findings are consumed by the active FIX/re-review loop. Resolved findings
remain history/evidence but do not become Release candidates merely because they
once existed.

## Release-time final recording

At Release, after semantic review/FIX convergence, give the accumulated
nonblocking findings to one bounded AI recording task.

That task may:

- consolidate duplicates across Steps/reviews;
- discard findings already resolved or made irrelevant by later implementation;
- classify the remaining items as Hygiene or Development Candidate;
- preserve useful evidence/rationale;
- update the project journal/candidate documents through the normal recording
  mechanism.

The recording task must not implement the candidates, broaden Release acceptance,
or start another recursive review/recording cycle. Recording a candidate is not
adoption.

This deferred recording reduces Step interruption and avoids multiple near-duplicate
candidate entries created from transient intermediate states.

## Evaluation for prospective Phase 6.5

Use Phase 6.4 as the current-workflow baseline. Do not add a heavy measurement
system. From existing workflow/evidence, compare what can reasonably be observed:

- number/rate of smell escalations;
- detector DECLINE rate;
- Detailed Review invocations and convergence loops;
- important Release findings missed by CLEAN triage;
- false-positive smell escalations that Detailed Review dismisses;
- REVIEW_FIX volume and implementation growth;
- duplicate/non-actionable findings eliminated by Release-time consolidation.

A Release finding should feed back to the cheapest appropriate harness:

```text
Release finding
  -> compiler/type/model improvement
  -> focused-test improvement
  -> Scala-lint rule
  -> CAR-lint rule
  -> Bad-Smell profile improvement
  -> conditional mandatory Detailed Review case
```

Prefer deterministic detection where possible. Keep Detailed Review for genuinely
semantic residuals.

## Phase 6.5 review questions

Before adopting this as Phase 6.5, review at least:

1. Can Step Admission safely treat compile/focused test/Scala lint/CAR lint as the
   normal deterministic gate without mandatory STEP_FULL AI review?
2. Is Bad Smell Detection sufficiently bounded that a cheaper independent model
   can perform it without turning it into another detailed review?
3. What minimal event/state change makes existing ReviewStep conditional while
   preserving explicit review escalation and repair?
4. Can pending finding lifecycle reuse current finding identities/history without
   introducing another ledger/snapshot system?
5. Can Hygiene/Development Candidate recording move to Release without losing
   information needed for current-Step decisions?
6. Does Release retain strong integrated assurance: cbd-support Review,
   comprehensive AI Review, bounded repair/re-review and Final?
7. Does the design demonstrably reduce review-induced scope expansion rather than
   merely moving the same review work to another label?

## Intended principle

Use strong deterministic harnesses for ordinary Step correctness, cheap independent
AI for anomaly triage, expensive AI for selected semantic convergence, and one
Release-time recording pass for residual nonblocking work.

The workflow should spend reasoning capacity where uncertainty actually remains,
rather than repeatedly asking an expensive reviewer to search every locally valid
Step for additional work.

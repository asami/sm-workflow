## Design decisions

Dependency source revision is a separately versioned native direction and
capture. Existing V1 dependency admission, capture and accepted-prefix formats
retain their meaning. The original primary base and accepted predecessor are
preserved. Adoption leaves a source pending fresh qualification; it does not
prove ancestry, accepted implementation or consumer completion.

The implementation connects the existing Decision supersession, candidate,
Git/File UoW, validation, review and closure owners. It retains per-path staging
intent/results and refuses uncertain effects. Content identity distinguishes
absence from empty files and detects byte drift without relying on Git status
alone. Independently declared exclusions, expected modes and exact check routes
guard selected input and unrelated index entries in every generation, including
already-staged no-op repair.

The existing consumption.programs vector supports exact primary and dependency
check workspace/kind/program routes. Native dispatch, actual receipts, retained
payload validation and interrupted-attempt reconciliation use the same route.
Partial dependency mappings are refused. Existing single-workspace behavior
and V1 schemas are retained.

Candidate recovery authenticates the exact revised-source prefix and offers
explicit ReviseWork/Defer. Fresh generations capture the chosen source anew;
old capture facts do not authorize stage replay or a new source successor.

Semantic result admission and retained-result decoding use the same selection
rule: dependency validation belongs to completed work without a competing Plan
or dependency proposal. A decision-needed result omits that selection. Invalid
combinations are refused before persistence so the authoritative projection
remains readable.

Issue assignment, review relevance and native check settlement use the existing
legacy-or-revised dependency binding projection. A source change retains the
original dependency TEST issue; only fresh matching checks can resolve it.
Independent review must continue to see it while it remains unresolved.

Public target and Git-change readers account for Record projection omitting
absent optional rename/blob fields. Required fields, unknown-field rejection
and blob/mode consistency remain enforced; public output can be read back
without weakening source-direction admission.

Source adoption clears current candidate and validation. The following repair
retains its authenticated failed-check context from the same Session, Plan,
primary base and Step, identifying the exact predecessor admission. It explains
the outstanding repair; it is not successful validation of the new source.
Explicit candidate `ReviseWork` uses the existing transition to ordinary
implementation work, without a repair check-failure payload. Both paths require
fresh candidate capture and checks.

Whole-Phase validation reconstructs its source-consumption route from the same
authenticated accepted dependency chain used during execution. Existing native
validation and recovery readers forward that chain through ephemeral inputs;
saved intent equality and public/stored schemas remain unchanged. Candidate
recovery retains prior Git effects, including an index mode whose stage result
was refused. Newly issued implementation work reconciles the actual worktree
and index before a fresh capture; the runtime does not replay the old intent.

## Runtime delivery and consumer continuation

Source qualification uses the ordinary current-source launcher. Installed
qualification explicitly selects the actual normally published immutable image.
Historical installed images cannot qualify newly authored APIs. Launcher tests
follow the selected source or installed branch while retaining exact operation,
single input, native output and failure expectations.

One coordinated canonical publisher owns normal publishLocal. The producer
reuses its complete accepted image for private qualification rather than
substituting individual JARs or replaying an updater request. Publication,
image association, executable qualification and actual consumer acceptance
remain separate results.

The structural host proposal retains old definitions and adds the new declared
source/check routes. Primary source-project environment changes apply only
after real public adoption. Normal discovery and valid bounded check groups
replace no acceptance obligations. Only the consumer's subsequent fresh checks,
independent review and ordinary closure can accept its source successor.

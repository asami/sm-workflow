# Phase 6.8 handoff: independent delegated development and delivery

Date: 2026-10-27
Audience: sm-workflow development and sm-workflow-dev development.
Status: approved specification/plan update; no implementation or installed claim.

## User decision

Create a planned `sm-delegate-task` entry with its own delegation contract.
Do not wrap sm-test-fix or sm-goal-task: their test scope and completion contracts
are already defined and must remain unchanged. Publication is outside those
skills' responsibilities. Reuse their common runtime execution mechanisms rather
than altering a child skill's contract after calling it.

The [delegate contract](../../../spec/delegate-task.md) and
[Phase 6.8 D1–D4](../../../phase/phase-6.8.md) assign verification selection,
commit, publishLocal and result delivery to sm-workflow. Localized work uses
applicable compile/focused tests and conditional review; broad uncovered impact
or explicit acceptance may require FULL. Cross-chat dispatch/publication alone
does not require FULL. Reuse actual checks/reviews; preserve FULL/HEAVY boundaries.

The user's follow-up makes local commit mandatory at successful delegate
completion. Uncommitted work is progress only; a no-change outcome identifies
the applicable existing commit and creates no empty commit. This does not change
standalone test-fix's own uncommitted-completion contract. Required publication
must also succeed before declaring the requested artifact delivery complete.

## Main route and development order

1. Reconcile actual 6.7 shared execution/delivery and 6.8 C1/C2 authority/recovery
   evidence. Define one delegation business request/result and CML public route.
2. Prove one selected existing destination: request -> shared implementation/FIX
   -> focused validation/acceptance -> commit -> runtime-owned publishLocal ->
   returned result -> requester adoption. Reuse C3 hygiene at the commit boundary.
3. Add runtime impact-based FULL selection, no-change/result reuse, publication
   failure continuation and return-transport interruption without duplicate effects.
4. Package the thin skill and matching public contracts/help, qualify the installed
   route, and hand the reusable single-request delivery to Phase 7.

Runtime owns necessity and effects; the caller transports issued dispatch/return
work where chat tools require it. No skill SBT, new chat API/context, polling or
second authorization/evidence/FIX ledger. Keep development, commit, publication,
return and consumer adoption separate. Producer publishLocal does not establish
consumer runtime activation. Reuse existing artifact attribution/selection.

## Phase boundaries and preservation

This adds D1–D4 and P68-15–22 to planned Phase 6.8, retaining C1–C5/P68-01–14.
Phase 6.9 owns both clean and dirty RepositorySync optimization. Phase 7 retains
dependency modes, durable FIFO, subtrees and explicit whole-Phase delegation;
it consumes 6.8 single-request delivery. Its previous text suggesting that
delegation extends test-fix/goal-task with publication is superseded.

Do not change active 6.7 acceptance or its original Task/FIX handoff contract.
Preserve all existing Sessions, bases, accepted results, histories, repair counts
and successful verification. In particular, the separately approved P67-T4
response031 adoption proceeds on its existing public route and does not wait for
this new skill or get re-Started as delegation. Existing actual cross-chat
evidence remains valid at its demonstrated scope; it is not automatically proof
of the new publication/validation-selection lifecycle.

Only planning/specification documents are changed here. Implementation, runtime
verification, normal publication/activation and active adoption are owned by the
development chats and must be reported from actual outcomes.

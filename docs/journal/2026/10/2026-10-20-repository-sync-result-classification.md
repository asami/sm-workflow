# Repository Sync の結果分類と利用者判断の報告

Date: 2026-10-20
Status: 利用者要望として記録。sm-workflow の報告機能への反映は今後の実装対象。

## 背景と合意

nict-editing-studio-app の Phase 6.2 後に行った8リポジトリの同期について、
「同期済み」という完了状態だけでは、変更の方向や統合時の判断が分からなかった。
利用者から、リポジトリごとの同期方法を分類し、衝突解消の中でも利用者判断を
要したものと、AIが解消できたものを区別して報告するよう要望があった。
sm-workflow の RepositorySyncWorkflow / sm-repository-sync の結果報告に取り込む。

関連設計: [SM Repository Sync Workflow Definition](../../../notes/sm-repository-sync-workflow-definition.md)

## リポジトリごとの基本分類

| 区分 | 利用者向けの表現 | 判定と報告内容 |
| --- | --- | --- |
| ① | GitHubを取り込んだだけ | リモート側だけに追加変更があり、ローカルへ取り込んだ。 |
| ② | ローカルの修正をGitHubに反映しただけ | ローカル側だけに追加変更があり、リモートへ反映した。 |
| ③ | 双方に修正があり、自動マージ | 双方の変更をGitが衝突なく統合できた。 |
| ④ | 双方の修正が衝突し、解消作業を実施 | Gitだけでは統合できず、AIによる解消または利用者判断を経て統合した。 |

公開ワークフローでは GitHub に固定せず、設定済みのリモート名に応じて表示する。
開始時点ですでに一致していて変更不要だったものは、その事実を別に表示し、
①から④へ無理に割り当てない。

「ローカル」には、今回の対象として選択された作業ブランチやworktreeの変更を含める。
通常チェックアウトの開始時点だけを見て、作業ブランチの変更を見落とさない。
分類には同期前の関係と実際の統合経路を使い、完了後の ahead/behind 0/0 から逆算しない。

## ④で必ず区別する判断の程度

| 判断の程度 | 意味 | 報告内容 |
| --- | --- | --- |
| 利用者判断が必要 | 仕様・計画・Phaseの識別や完了状態など、複数の妥当な選択肢や権限上の判断がある。 | 選択肢、利用者が承認した方針、適用結果を短く示す。 |
| AIによる技術判断 | 既存の仕様と承認範囲から解消できるが、コードやテストの整合性について判断が必要。 | 対象、維持した双方の意図、実施した検証・レビューを示す。 |
| 軽微な衝突解消 | 独立した追記を両方残すなど、仕様の選択を伴わない解消。 | 両方の追記を保持した、など実際の処理を示す。 |

Gitによる③の自動マージと、AIが④の衝突を自律的に解消したことを、どちらも
「自動マージ」と呼んで混同しない。ファイル数や差分量だけで判断の程度を決めない。
同じリポジトリで複数の解消方法を使った場合は、その内訳も説明する。
利用者判断は実際の回答・承認に基づいて記録し、AIによる判断を利用者承認と表現しない。
Gitが衝突を報告しなかった場合も、別途意味上の不整合を発見して判断・修正したなら、
その追加作業を明記し、「自動マージだけで完了」と報告しない。

## 報告形式

最終報告では、リポジトリ、基本分類、判断の程度、統合内容の短い説明を表にする。
①から④の件数と、④のうち利用者判断を要した件数も示す。
同期前の分類と、同期後の一致・未コミット変更の有無は別の情報として示す。
検証は実際に実施した範囲と結果を記載する。判断経路や検証が未確認なら未確認とする。
同期とは別に承認された履歴整理などは、分類とは別欄に記録する。

## 今回の8リポジトリでの具体例

| リポジトリ | 基本分類 | 判断の程度 | 統合内容 |
| --- | --- | --- | --- |
| simplemodeling-lib | ② | 衝突なし | ローカルの承認済み修正を反映。 |
| simple-modeler | ② | 衝突なし | ローカルの承認済み修正を反映。対象ブランチはscala12。 |
| cozy | ④ | AIによる技術判断 | テスト3ファイルを双方の検証内容を維持して統合。対象34テスト成功、独立レビュー実施。 |
| cloud-native-component-framework | ④ | AIによる技術判断 | テスト・補助コード6ファイルを統合し、残った参照不整合を修正。修正後の対象191テスト成功、独立レビュー実施。 |
| nict-knowledgehub | ③ | Gitによる自動マージ | ローカルの実装修正とリモートの設計・計画文書を衝突なく統合。 |
| nict-editing-studio | ④ | 利用者判断が必要 | 承認に基づき、Phase 3の新4ステップ案を軸に旧8ステップ案の要件を統合。 |
| textus-flutter-application-framework | ④ | 利用者判断が必要 | 承認に基づき、完了済みPhase 3を保持し、別テーマSensitive Interactionを未着手Phase 4へ移動。 |
| nict-editing-studio-app | ④ | 軽微な衝突解消 | material-model-and-mobile-material-editor.mdの独立した追記を両方保持。 |

集計: ①0件、②2件、③1件、④5件。④のうち利用者判断2件、AIによる技術判断2件、
軽微な衝突解消1件。これらは2026-10-20の同期結果であり、sm-workflowでこの報告機能が
実装・検証済みであることを示すものではない。

TFAFの過去ログ1件を未送信履歴から除去した作業は、別途明示承認された履歴整理として
扱う。元の履歴とログはローカル保管済みで、通常pushを使用した。この例外から
RepositorySyncWorkflow一般の履歴書換え権限を導かない。

## 今後の実装・受入れ観点

- 同期前の関係、Gitの統合結果、AIの解消結果、利用者のDecisionから分類を報告できる。
- 利用者判断とAIの技術判断、Gitの自動マージを区別して表示できる。
- 複数リポジトリの一覧と件数が一致し、変更不要や未完了も事実どおり表示される。
- 報告のためにGit操作や利用者への質問を再実行せず、保存済みの実行結果を用いる。

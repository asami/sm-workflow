# Phase 6.10 cost profile refinement: preserve the active run

Date: 2026-11-02
Status: planning handoff; not a live configuration change or implementation receipt.
Audience: sm-workflow development and sm-workflow-dev development.

## Authorized direction

The user accepts conservative standard settings and wants a more differentiated
cost candidate that can use Low where decisions are already settled. Record this
in Phase 6.10 without disturbing the running development, existing Sessions or
successful evidence. Both checkouts retain their own existing documentation and
source changes; only the new cost planning sections are synchronized.

## Intended mapping

- Deterministic work: runtime operations, no AI. Eligible small clear repairs:
  retain parent INLINE; do not create a worker merely to use a cheaper model.
- Exact prescribed mechanical transformations with settled semantics: Luna Low.
- Hygiene requiring bounded interpretation of explicit rules: Luna Medium.
- Small ordinary implementation/repair with cause, solution and intended behavior
  already established: Terra Low.
- Ordinary implementation/repair, bounded investigation/initial diagnosis and
  required local review/re-review: Terra Medium.
- Difficult implementation, cause analysis and design, plus Phase/Release
  integrated review: Sol High. Hardest interacting judgments: Sol XHigh.
- Parent settings, acceptance, tests, review triggers/independence and repair
  trend/limits remain unchanged. This is not a measured savings claim.

Do not create extra parent reasoning or a lengthy new fix recipe solely to use
Low. A one-line expectation change is not mechanical until its semantics are
established. Preserve the existing independence requirement for reviews.

## Availability

The new cost revision explicitly permits Terra Low -> Sol Low, Terra Medium ->
Sol Medium, and Terra High -> Sol High when High is configured. These are captured
cost-owned edges, not implicit standard fallback. Missing alternatives stay
unavailable; unsupported effort follows only an explicitly captured next edge.
Existing issued cost mappings retain their original semantics.

Use actual caller capability evidence or confirmed pre-execution model rejection.
No paid probe, automatic model upgrade after a task failure, replay of uncertain
work, or repeated Human permission for the same covered work. Preserve actual
requested/resolved/observed model and effort and fallback reason in existing
records. Policy/permission refusal and invalid config are not model absence.

## Delivery and adoption

1. Continue current M3, recovery and existing M2A/M4 work. Do not interrupt or
   reopen accepted work, mutate live Session/Plan, change config or replace a
   pending worker because this planning document was added.
2. At an appropriate unissued development boundary, reuse M2/M2A and the caller
   adapter to implement supported mapping-only C1/C2 portions. Keep the native
   classification/profile ownership and runtime Git/SBT/publication routes.
3. Use focused selection/dispatch/retention tests and applicable existing adapter
   evidence and integrated review. If a candidate needs additional runtime
   machinery, identify it in a linked follow-up, retain the supported mapping,
   and leave it deferred. Do not add a new completion gate to the current 6.10.
4. After qualification, use the revision only for explicitly selected cost and
   newly issued work. Preserve existing Goal/Session/Plan, accepted results, full
   history, repair counts and successful validation; no re-Start, accepted-result
   re-Submit, counter reset or success replay.
5. Observe total consumption including repair/retry, completion time, first-pass
   and eventual success from existing comparable normal-work records. Include
   failed attempts and partial coverage, separate Codex/local usage and mixed
   revisions. No duplicated benchmark work or mandatory live Terra run.

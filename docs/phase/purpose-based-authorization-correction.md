## Acceptance scenarios

- Same Component/purpose/acceptance/operations, two additional completion-owner
  files: AI submits the reason, runtime admits, no new Human request, same work
  continues. Cover implementation, repair and necessary test-file additions.
- Different Component, unrelated purpose, acceptance change, new operation or
  explicit excluded file: actual runtime decision identifies the changed boundary;
  the skill relays the Human request instead of independently granting permission.
- Malformed request or unavailable capability: typed failure/gap, not fabricated
  missing consent. Do not infer Component membership from a directory prefix.
- New files are present in the new actual candidate and affected validation;
  unrelated dirty files and planned-but-absent files are not staged. New source
  does not inherit an old PASS as if it had already been validated.
- Repeated Submit/Advance follows existing idempotence/history semantics without
  duplicate questions/effects. Unknown effects retain their existing handling.
- An active legacy Session adopts publicly: identity, original base, accepted Steps,
  old approvals/rejections, attempt history, repair counts and test evidence survive.
  No replay of accepted work, counter refund or blanket retest is introduced.
- Source skill and packaged skill have matching rules; actual installed runtime
  emits the expected request/continuation and the caller does not add its own gate.
